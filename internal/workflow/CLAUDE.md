# internal/workflow — Task Execution Engine

Step execution, template resolution, step context capture, merge/conflict handling. Load `/workflow` skill before making substantial changes.

## Critical Invariants

- **Step context comes from the agent's result text, stored in DB after each step** — headless steps read it from `$SAKUSEN_RESULT_FILE` (stdout-tail fallback); tmux steps with `summarize_chat` get their chat via the agent record's `chat_log_command`. Synchronous capture; step index persisted
- **`{{chat}}` for a headless step is the agent's STREAMED OUTPUT ONLY, never the echoed prompt** — `loadStepChatContent` slices the step's task-log region and then strips the header, the prompt block (bounded by the single literally-empty line `runHeadlessAgent` writes after it), and the footer. An agent that redirects stdout into `$SAKUSEN_RESULT_FILE` — the documented env contract — streams nothing, so this correctly yields `""` and `summarize_chat` is skipped, keeping the result text. Feeding the prompt back in made the summarizer summarize sakusen's own instructions and overwrite the real result; `smallChatBytes` is no protection because a long prompt clears it
- **Loop exit conditions: prefer `step_context_contains` or `command` over `step_context_empty`** — exiting on an absence cannot distinguish "the step decided the work is done" from "the step crashed, timed out, or forgot to publish", so every one of those silently ends the loop and ships. A marker requires a positive statement; a step that fails to run leaves it absent and the loop continues, bounded by `max_iterations`. A `command` (`loopexit.go`) is three-way: exit 0 ends the loop, 1 continues, and any other status, a timeout or a start failure FAILS the task — it never silently continues or ends. The output tail is logged to the task log on every outcome
- **At `max_iterations` the exit conditions are skipped unless `on_max_iterations: fail`** — the default falls through to the next step with the condition unmet; `fail` evaluates them on that pass (a command still keeps its 0/1/other contract) and fails the task when none matches, logging the reason to the task log
- **`loop.goto` may name an earlier step or the loop step itself** — a self-loop takes the same `stepOutcomeGoto` path with `gotoIdx == i`, so the step re-runs with `{{loop.iteration}}` incremented and its exit conditions, `max_iterations` and `on_max_iterations` apply exactly as for a multi-step loop
- **`t.LoopIteration` is reset to 0 on loop exit** — so `{{loop.iteration}}` and the TUI badge do not leak into post-loop steps. That erases the pass count, so `runStep` writes a `=== Loop … completed after N iteration(s) ===` line to the task log first (via `Engine.appendTaskLog`); the task log is the durable record, not the DB
- **The tmux sentinel convention is generic** — the engine exports `SAKUSEN_DONE_DIR` (`StepDoneDir`) and `SAKUSEN_DONE_PREFIX` (`SentinelPrefix(step)`); whatever runs in the session (a hook, the agent, an idle-watcher) signals turn-end by writing `$SAKUSEN_DONE_DIR/$SAKUSEN_DONE_PREFIX-<ts>.json`, whose optional JSON payload may carry `session_id`/`transcript_path`. Core installs NO Stop hook — hookless tmux agents are manual-advance
- **A parallel group's row is ENGINE-OWNED and its branch rows are never re-run once completed** — `runParallelGroup` (parallel.go) fans out to the group's branches on one worktree, applies the manual > last_message precedence per branch, runs any `summarize_chat` passes sequentially AFTER the join (never inside a branch goroutine), and returns `FormatParallelAggregate(...)` as the group's result text. `captureHeadlessStepContext` short-circuits for groups and stores that text verbatim — re-running the precedence chain there would let a manual write, or a summarize pass over a log the group never wrote, replace the aggregate. Because a `completed` branch row is skipped on the next pass, whoever wants a re-run deletes rows first: the daemon's retry handler drops the retried group's row plus its NON-completed branch rows (so retrying a group re-runs only its losers) and every branch row of any later group, and `applyStepResult`'s loop-goto path drops ALL branch rows of any group inside the loop range (so the next iteration re-runs the whole group). `runSummarizer` deliberately collects TOP-LEVEL step names only — the group row already contains every branch, so adding branch rows would double-count them
- **Branch agent output never enters the unified task log** — each branch spawns with a `headlessSpawn{LogPath, OutputFile, Tag}`: its own `branch-<name>.log` (identical region layout, so `stepAgentOutput` slices it unchanged), its own `<worktree>/.sakusen/output-<branch>.log` raw capture (`runner.Process` truncates its output file on start, so concurrent branches would clobber a shared one), and a `[<branch>]` tag inserted after the timestamp of every line forwarded to the LIVE stream. `task.log` receives only the two `=== parallel <group>: ... ===` marker lines, so the live view and task.log deliberately differ for the group's duration
- **An isolated group (`isolation: worktree`) runs each branch on a task COPY with `WorktreePath`/`Branch` swapped to `IsolatedBranchWorktreePath`/`IsolatedBranchGitBranch` (`<task>-<name>`)** — `runBranch` acquires a slot from `Engine.branchSlots` (the `SetBranchSlots` seam; nil means unlimited), calls `repo.EnsureWorktreeAt` from the task worktree's HEAD, then `populateWorktree` (sync paths, setup commands, work dirs, images) on the copy; rows, logs and manual context stay keyed on the shared task ID. On exit 0 it commits via `repo.Commit` (`sakusen: task #N branch <name>`; a clean tree is a no-op, a failed branch is never committed). Under `require: N`/`any` siblings are cancelled only once N is unreachable, never on success; `require: all` stays fail-fast. A task with `worktree: false` fails the group at runtime with `isolation: worktree requires a worktree` (config validation catches workflow/routine pins). Every step prompt (branch prompts included) locates a branch via `{{branches.<name>.branch}}` / `{{branches.<name>.worktree}}`, built by `isolatedBranchVars` from the workflow config (`""` for unknown names and shared-group branches). The daemon wires `SetBranchSlots` to `agent.Manager`, so each task's first held branch slot borrows the task's own `max_workers` slot and every further one counts against `max_workers`. Retry and loop-back reuse an existing branch worktree as-is (`EnsureWorktreeAt` never discards one). `RemoveIsolatedBranchWorktrees` derives paths from the workflow config and `t`, not from DB rows, so the delete path works after the row is gone — and editing a workflow (renaming/removing an isolated branch) orphans that branch's worktree
- **A fanout step runs NO agent; its children are spawned through the daemon's `FanoutHost`** — `runFanoutStep` (fanout.go) reads the items the `from:` step published via `publish_items` (`GetPublishedItems`), renders each child's `input` with `ItemVars` (`{{item.input}}`/`slug`/`title`/`index`, 1-based) and calls `FanoutHost.SpawnChild` in `task.TopoOrder` so every `needs` blocker already has a child to wire as `blocked_by`. The engine never creates tasks itself; with no host set (`SetFanoutHost`) the step fails. Spawning is idempotent through the DB's unique `(fanout_parent_id, fanout_step, fanout_item)` index: an item that already has a child is skipped, and a spawn that loses to the index reuses the existing child — that is what makes a daemon restart or a parent retry safe
- **The fanout join reads the fanout columns, not the `task_waits_on` edges** — children are looked up with `GetFanoutChildren(parent, step)`; `AddTaskWaitsOn` edges are written only so the parent suspends in `awaiting-children` and the daemon wakes it. Re-entry with the step row still `running` is a RESUME (a failed child is retried while `fanout_attempts < retries`); any other entry is FRESH (first run, parent retry), which resets every failed child's attempts and retries it. Cascade-failed dependents (`error_message` starting `blocker task #`) go back alongside their retried blocker without spending attempts. Once all children are terminal, `require` (`config.RequiredCount`) decides: met → `FormatFanoutAggregate` becomes the step's result and the task advances; unmet → the task fails listing `<slug> #<id>` per failed item. A `require` above the item count fails before spawning
- **A fanout source's published list is cleared whenever that step starts** — `runStep` calls `ClearPublishedItems` for any step named in a fanout's `from:`, so a re-run (retry, loop) can never fan out a stale list; a headless source that completes without publishing fails the task (tmux sources are caught by the fanout's own missing-items check)
- **A `nodes:` fanout is driven by `runFanoutNodes`, which spawns each node only when it is ready** — there are no published items and no `blocked_by` edges: every pass walks `NodeTopoOrder`, and a node with no child whose needs all have `completed` children spawns NOW, its `input` rendered at that moment against a template context whose `Steps` map includes the fresh node contexts (`ItemVars{Slug, Title: name, Index: i+1}`, `item.input` empty). Each pass first runs `retryFanoutNodes` (per-node `EffectiveNodeRetries`; FRESH entry resets attempts and retries every failed child, RESUME only while `fanout_attempts` is below the node's retries), then rewrites one parent `task_steps` row per node from its child's state — completed → row with the child's context, anything else → row deleted — so `{{steps.<node>.context}}` never shows a stale retry. A node behind a need whose child failed for good (or was itself skipped) is never spawned, counts as failed at the join, and is passed in `FormatFanoutAggregate`'s `skipped` map (`- <node> (skipped: need <need> failed)`). The step suspends while any child is non-terminal or any node is still waiting; duplicates are impossible through the same `(fanout_parent_id, fanout_step, fanout_item)` index, a losing spawn reusing the existing child
- **Fanout nesting is capped at `config.MaxFanoutDepth` (3), enforced at spawn** — `GetFanoutDepth` counts `fanout_parent_id` hops; a task at the cap fails its fanout step without spawning
- **The merge invariant lives in `internal/merge`** — serialization, conflict retry, and the target-ready wait (main clean and on base) are owned by `*merge.Coordinator`; the engine only calls `e.coord.Finalize(ctx, t, baseBranch, logFn)`
- **Agents start in `AgentWorkDir(t)`, sakusen's files stay at `t.WorktreePath`** — `workdir.go`'s helper joins the checkout root with `t.Workdir`; every agent-start site (headless `runner.Process` dir, parallel branches, tmux session `-c` and setup-command cwd, `chat_log_command`, a loop `exit_condition` command, and the daemon's `spawnInteractiveSession`) goes through `ResolveAgentWorkDir`, which fails the spawn when a set workdir is missing. `.sakusen/` (prompt/result files, sentinels, raw output logs), worktree setup commands, `SAKUSEN_WORKTREE`, `{{worktree_path}}`, the summarizer and the merge-conflict agent all stay at the root; `{{task.images}}` paths are relative to the start dir
- **Non-worktree mode skips branch creation, uses project root** — `on_complete` falls back to `Commit()` (or no-op) instead of merge; the Coordinator enforces this when `t.Worktree == false`
- **A broken `{{prompt.<name>}}` include FAILS the step; it is never left verbatim** — `ResolveTemplate` returns `(string, error)`: it expands includes (against `ctx.PromptDirs`, project-then-global) BEFORE the placeholder pass, so an included passage resolves its own `{{task.*}}`/`{{steps.*}}` in the same pass, and errors on a missing file, a malformed name, or a nested include (depth is 1). Unknown ordinary placeholders still pass through verbatim — an unresolved *include* does not, because a prompt with a literal `{{prompt.x}}` in it reaching an agent is worse than not running. The config loader and `sakusen validate` already reject these at load time; the runtime check covers files deleted since. Includes are read from DISK per step launch, so `internal/config` snapshots only the dirs (`engineConfig.PromptDirs`), never the contents
- **`{{track.*}}` vars are explicit opt-in and read LIVE per step** — `runStep` re-reads the task's track chain (`GetTrackChain`, root-first) at every step launch so mid-run track context updates reach later steps; retries may therefore render different prompts than the original run (accepted). Trackless tasks resolve all `{{track.*}}` vars to `""`; track context is never injected into a prompt automatically.
