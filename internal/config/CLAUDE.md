# internal/config — Configuration

`.sakusen.yml` parsing, project type detection, workflow definitions. Load `/config` skill before making substantial changes.

## Critical Invariants

- **Loop goto must reference an earlier step** — validated at parse time; forward jumps or self-references create infinite loops
- **Summarization strategy affects step context capture** — `last_message` keeps the headless agent's result text; `summarize_chat` runs the configured `summarizer:` command over the chat log
- **Config merge hierarchy is strict** — `.sakusen.yml` > `~/.sakusen.yml` > global defaults; invalid configs halt the CLI
- **Agents merge per-slug across tiers** — `mergeAgents` overlays the project-tier `agents:` map onto the global tier; a slug redefined more locally wins wholesale (records are never field-merged, and a redefinition replaces the record's `variants:` too). `resolveAndValidateAgents` runs in `Load()`/`LoadForProject()` only AFTER all tiers and workflows are merged, in order: user-authored record validation (kebab-case slug, required `command`, mode ∈ {headless, tmux}, `resume_command`/`chat_log_command` tmux-only, variant declarations) → variant expansion → alias resolution → ref validation (explicit `agent:`/`default_agent:` refs must resolve — the implicit `"claude"` fallback is exempt and fails at step-run time instead — loop steps must not resolve to tmux agents, and `{{claude_command}}` in tmux-setup-command is rejected).
- **Agent variants expand into flat registry entries** — `agents.<parent>.variants.<name>` declares a partial record that inherits every parent field and overrides only what it redefines (`env` merges per-key, variant wins; all other fields override wholesale; a variant cannot unset a parent field). `expandAgentVariants` inserts each as an ordinary entry under `<parent>:<variant>` and clears `Variants` on stored records, so downstream code just sees more agents. Variants are one level deep (nested `variants:` is a hard error); a user-authored colon key under `agents:` is rejected (only expansion creates them); the resolved variant record is shape-checked post-inheritance.
- **Agent aliases are a top-level routing map** — `agent_aliases:` (alias → target slug) merges per-key across tiers (more-local wins). `resolveAgentAliases` runs after variant expansion and inserts a copy of the target's record under the alias name, so an alias works anywhere an agent slug does; targets may be plain agents or `parent:variant` slugs. Alias names are plain kebab-case (no colons); collisions with existing registry keys, unknown targets, and alias→alias chains are load-time errors.
- **Removed keys are hard migration errors** — `claude:`, `yolo:`, `system_prompt:`, `allowed_summarization_models:` (top-level, via `checkRemovedProjectKeys` on the raw YAML; also step-level for the last one), and `print:`/`tmux:` (workflow and step level) all fail the load with instructive messages pointing at the `agents:`/`summarizer:` replacements — no silent back-compat mapping.
- **Track workflows are hidden and namespaced** — `.sakusen/tracks/<slug>/workflows/*.yml` (project tier) and `~/.sakusen/tracks/<slug>/workflows/*.yml` (global tier) register as `Hidden: true` workflows named `<slug>:<name>` via `appendTrackWorkflows`, called AFTER project-level resolution in `Load()`/`LoadForProject()` (never inside `loadProjectConfig`, which also runs for `~/.sakusen.yml`). Project shadows global on identical namespaced names; there is no implicit same-name shadowing of ordinary workflows — track workflows are only reachable via their namespaced name.
- **Project string refs fall back to a global workflow pool** — after `~/.sakusen.yml` is loaded, its resolved workflows (both inline and file-based under `~/.sakusen/workflows/`) are snapshotted into `cfg.globalPool`. Project-level string refs in the flat `workflows:` list try the local `.sakusen/workflows/` pool first, then `cfg.globalPool`. A project may override a global workflow by defining it inline or by adding a local `.sakusen/workflows/<name>.yml`. Inline-vs-file collision is enforced only within a single config scope.
- **`on_complete` resolution is locality-based** — `Config.EffectiveOnComplete(workflowName)` is the single resolution point (the engine delegates to it). Precedence: project-scoped workflow `on_complete` > explicit project-level `on_complete` > global workflow `on_complete` > inherited/global/default. Workflows adopted from the global pool (and global-tier track workflows) are marked `FromGlobal: true` by the loader; `Config.OnCompleteFromProject` records that the project-tier `.sakusen.yml` explicitly set `on_complete`. A global workflow's `on_complete` is a cross-project *default*, never a silent override of a project's explicit choice.
- **Step references mirror workflow references** — inside a workflow's `steps:`, a bare-string entry (`- planning`) is a *step reference* resolved by `resolveWorkflowSteps` against the same-named workflow in `cfg.globalPool` (the workflow this one overrides). Inline step mappings pass through; an inline step whose name matches a base step fully overrides it (replace-not-merge). Dropping a step = omitting it; adding = an inline entry with a new name. A ref to a step absent from the base — or a ref with no base workflow at all — is a hard error. A bare-string step is parsed via `StepConfig.UnmarshalYAML` (scalar → `StepConfig{Name, ref:true}`) and always resolved to a concrete step before validation.
- **Workflow entries have three shapes, all routed through `resolveFlat`** — an entry in the flat `workflows:` list (`WorkflowEntry`) is a scalar ref, a `- name: X` inline def, or the named-body sugar `- X: { ... }` (single key that isn't a known `WorkflowConfig` field; empty body = bare ref). `Diagnose`'s global-pool load is tolerant: a malformed/unresolvable `~/.sakusen.yml` yields no pool rather than failing project validation.
