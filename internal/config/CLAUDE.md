# internal/config — Configuration

`.sakusen.yml` parsing, project type detection, workflow definitions. Load `/config` skill before making substantial changes.

## Critical Invariants

- **Loop goto must reference an earlier step** — validated at parse time; forward jumps or self-references create infinite loops
- **`exit_condition` has two forms; prefer the affirmative one** — `step_context_empty: <step>` exits on an ABSENCE and so cannot distinguish "done" from "the step crashed / timed out / forgot to publish", each of which silently ends the loop and ships. `step_context_contains: <step>` + `marker: <literal>` requires the step to state completion; a step that fails leaves the marker absent and the loop continues, bounded by `max_iterations`. Both may be set (exit when either matches); `marker` is required with `step_context_contains`, and an `exit_condition` block that sets neither form is a load-time error
- **Summarization strategy affects step context capture** — `last_message` keeps the headless agent's result text; `summarize_chat` runs the configured `summarizer:` command over the chat log
- **Config merge hierarchy is strict** — `.sakusen.yml` > `~/.sakusen.yml` > global defaults; invalid configs halt the CLI
- **The project root is the nearest ancestor `.sakusen.yml`** — `FindProjectRoot()` (`projectroot.go`) walks up from cwd to the first directory holding a marker, bounded by the git toplevel (itself checked, and the fallback when no marker is found), so a `.sakusen.yml` below a repo root owns its own project. `Load()`, the TUI's `resolveProjectMode` and the MCP server's `resolveProjectPath` all go through it, so they always agree on the project row
- **Agents merge per-slug across tiers** — `mergeAgents` overlays the project-tier `agents:` map onto the global tier; a slug redefined more locally wins wholesale (records are never field-merged, and a redefinition replaces the record's `variants:` too). `resolveAndValidateAgents` runs in `Load()`/`LoadForProject()` only AFTER all tiers and workflows are merged, in order: user-authored record validation (kebab-case slug, required `command`, mode ∈ {headless, tmux}, `resume_command`/`chat_log_command` tmux-only, variant declarations) → variant expansion → composed-ref expansion → alias resolution → ref validation (explicit `agent:`/`default_agent:` refs must resolve — the implicit `"claude"` fallback is exempt and fails at step-run time instead — loop steps must not resolve to tmux agents, and `{{claude_command}}` in tmux-setup-command is rejected).
- **Agent variants expand into flat registry entries** — `agents.<parent>.variants.<name>` declares a partial record that inherits every parent field and overrides only what it redefines (`env` merges per-key, variant wins; all other fields override wholesale; a variant cannot unset a parent field). `expandAgentVariants` inserts each as an ordinary entry under `<parent>:<variant>`, returns the per-parent declarations snapshot, and clears `Variants` on stored records, so downstream code just sees more agents. A user-authored colon key under `agents:` is rejected (only expansion creates them); every resolved record is shape-checked post-inheritance; nested `variants:` is still a hard error.
- **A ref may stack any number of a parent's variants as modifiers** — a ref is `parent[:modifier]*` and the modifier set is order-independent: `canonicalAgentRef` sorts the modifiers alphabetically into the registry key, and `ResolveAgent` canonicalizes before lookup (authored refs in config structs are never rewritten). `expandComposedAgentRefs` runs after variant expansion and before alias resolution over exactly the refs the config mentions (`default_agent`, workflow/step `agent:`, alias targets — including hidden track workflows, which are appended before `resolveAndValidateAgents`), so the cross product is never materialized. Each modifier must be a variant declared by that parent; two modifiers setting the same field or env key to different values is a load error (identical values compose), which is what makes application order irrelevant. Duplicate modifiers, unknown modifiers, and composed records failing shape validation are load errors.
- **Agent aliases are a top-level routing map** — `agent_aliases:` (alias → target slug) merges per-key across tiers (more-local wins). `resolveAgentAliases` runs after variant and composed-ref expansion and inserts a copy of the target's record under the alias name, so an alias works anywhere an agent slug does; targets may be plain agents, `parent:variant` slugs, or composed refs (resolved through `ResolveAgent`, so any modifier ordering works). Alias names are plain kebab-case (no colons); collisions with existing registry keys, unknown targets, and alias→alias chains are load-time errors.
- **System-role blocks reference registry agents** — `summarizer:` (`agent:`/`slug_agent:`, or the bare `command:`/`slug_command:` alternative) and `merge_conflicts:` (`agent:`, `timeout:`, `prompt:`) hold role-specific knobs and pick a runner from `agents:`. Both merge WHOLESALE across tiers (`overrideFromPtr`, like `summarizer:` always did). `validateRoleBlocks` enforces the file-local rules (agent/command exclusivity, timeout parseability) in both the full load and single-file diagnosis; `validateAgentRefs` additionally requires every role agent slug to resolve and be headless. Resolution: `Config.MergeConflictAgentFor(wf)` (`merge_conflicts.agent` → workflow `agent:` → `default_agent:` → `"claude"`, with the tmux→headless-`"claude"` fallback on the lower tiers only) and `Config.SummarizerInvocation()`/`SummarizerSlugInvocation()` (agent record vs bare command).
- **A top-level `tmux:` block configures session hibernation, daemon-level** — `hibernate_after` (duration string, default `4h`) and `max_live_sessions` (`*int`, default `12`) merge PER FIELD across tiers (`applyTmuxConfig`), so a tier may set one key without resetting the other and an explicit `0` disables rather than reading as unset. An unparseable duration or a negative value is a hard load error, reported by `sakusen validate` through the same helper. The daemon reads the resolved values from its own `Config` exactly like `max_workers` — there is no per-project override at runtime. Unrelated to the still-removed workflow/step-level `tmux:` key below.
- **A top-level `merge:` block configures the clean-target wait** — `clean_target_timeout` (duration string; empty inherits, `0` = wait forever, the default) and `ignore_paths` (git glob pathspecs; a non-empty list replaces the inherited one) merge PER FIELD across tiers via `applyMergeConfig` into `Config.MergeCleanTargetTimeout` / `MergeIgnorePaths`, which the workflow engine passes to `merge.Config`. An unparseable/negative duration or an empty pattern is a hard load error, also reported by `sakusen validate`. `notifications.on_merge_blocked` (default false) gates the merge-blocked desktop notification.
- **`git.verify_command` / `git.verify_timeout` gate `on_complete: merge`** — both override per key across the `.sakusen.yml` tiers like `base_branch` (the XDG `config.yaml` has no `git:` block). `verify_timeout` (duration string; empty inherits, default `DefaultGitVerifyTimeout` = 15m, `0` = no limit) resolves via `applyGitVerifyTimeout` into `Config.GitVerifyTimeout`; an unparseable/negative value is a hard load error, also reported by `sakusen validate`. The workflow engine passes both to `merge.Config`; empty `verify_command` disables verification.
- **Removed keys are hard migration errors** — `claude:`, `yolo:`, `system_prompt:`, `allowed_summarization_models:`, `merge_conflict_agent:`, `periodic:` (top-level, via `checkRemovedProjectKeys` on the raw YAML; also step-level for `allowed_summarization_models`), and `print:`/`tmux:` (workflow and step level) all fail the load with instructive messages pointing at the `agents:`/`summarizer:`/`merge_conflicts:` replacements — no silent back-compat mapping.
- **`routines:` are BINDINGS, `workflows:` are DEFINITIONS** — a `RoutineConfig` names a workflow, supplies pins and at most one trigger (`cadence:` or `after: <routine>`), and may never define steps (`steps`/`agent`/`summarizer_prompt`/`exclusive_workdir` on a routine are load errors; `periodic:` is a removed key). `validateRoutines` runs in `Load()`/`LoadForProject()` right after `appendTrackWorkflows` (and in `validateProject` against a scratch copy with track workflows appended), once every workflow tier is assembled, and resolves the ref with `findWorkflowByName` — so a hidden pool file or a `<slug>:<name>` track workflow is a legal target. `RoutineConfig.EffectivePins(wf)` is the single merge point: input/worktree/target/workdir merge per field, branch and checkout merge as a PAIR (setting either on the routine ignores both of the workflow's), mirroring how an explicit request value displaces a workflow pin in `createTaskFromRequest`. The daemon passes those pins explicitly on the create request, which is what lets one workflow back several differently pinned routines.
- **A routine's input requirement is emergent, not declared** — `Config.RoutineRequiresInput` is true when the effective input is empty AND the workflow references `{{task.input}}` in any step or parallel-branch prompt. That state is a LOAD ERROR for a triggered routine (cadence or after — an automatic fire has nobody to ask) and legal for an on-demand one, whose run surfaces demand the argument instead; the daemon re-checks it in `fireRoutine`, so it holds however the routine is fired.
- **`after:` chains routines** — `after: <routine>` fires each time a run of that same-project routine (scheduled, triggered or on-demand) reaches `completed`; it is mutually exclusive with `cadence:`, and `validateRoutineAfter` rejects unknown names, self-references and cycles.
- **Hidden stays a placement property** — there is no `hidden:` field. A pool file listed in `workflows:` is visible, one that isn't is hidden, and one referenced by a routine is hidden but reachable — the routine is what makes it startable, so `Diagnose` suppresses the "is hidden" warning for it.
- **Track workflows are hidden and namespaced** — `.sakusen/tracks/<slug>/workflows/*.yml` (project tier) and `~/.sakusen/tracks/<slug>/workflows/*.yml` (global tier) register as `Hidden: true` workflows named `<slug>:<name>` via `appendTrackWorkflows`, called AFTER project-level resolution in `Load()`/`LoadForProject()` (never inside `loadProjectConfig`, which also runs for `~/.sakusen.yml`). Project shadows global on identical namespaced names; there is no implicit same-name shadowing of ordinary workflows — track workflows are only reachable via their namespaced name.
- **Project string refs fall back to a global workflow pool** — after `~/.sakusen.yml` is loaded, its resolved workflows (both inline and file-based under `~/.sakusen/workflows/`) are snapshotted into `cfg.globalPool`. Project-level string refs in the flat `workflows:` list try the local `.sakusen/workflows/` pool first, then `cfg.globalPool`. A project may override a global workflow by defining it inline or by adding a local `.sakusen/workflows/<name>.yml`. Inline-vs-file collision is enforced only within a single config scope.
- **`on_complete` resolution is a most-specific-wins cascade** — `Config.EffectiveOnComplete(workflowName)` is the single resolution point (the engine delegates to it). Precedence: workflow `on_complete` > project-level `on_complete` > global-level/built-in default. Scope does NOT enter into it: a workflow adopted from the global pool (marked `FromGlobal: true` by the loader, which is provenance only) has its `on_complete` honored exactly like a project-defined one, because `on_complete` describes the workflow's shape (whether its last step is a human gate). A project that needs a different value for a global workflow shadows it by name and sets `on_complete` there.
- **Notification overrides cascade per field: routine → workflow → global; `enabled` is global-only** — `notifications:` on a workflow or routine (`NotificationOverrides`, all `*bool` plus `notify_if`) is resolved by `Config.EffectiveNotifications(workflow, routine, base)`, the single resolution point; the first tier that sets a field wins, and a missing routine/workflow is skipped. The global `enabled` is never overridable (no key exists), so an override can silence events but never turn notifications on. The block and its `notify_if` decode strictly via `checkKnownMappingKeys`, because their parent entries tolerate unknown keys; `notify_if` must use exactly one form and name a step or branch of the bound workflow.
- **A `parallel:` step is a GROUP, and `EffectiveBranch` is its ONLY normalization point** — `StepConfig.Parallel` (`ParallelConfig{Require, Branches []StepConfig}`) turns an entry into a fan-out container. `ValidateSteps` rejects a group that sets `prompt`/`loop`/`human`/`advance`/`summarization_strategy`/`summarization_prompt`/`require_context` (all belong on a branch), a group with zero branches, a `require` outside `""`/`all`/`any`/`1..len(branches)`, a branch that is itself a group / has a `loop` / has `human` / sets `advance` / is a bare-scalar step reference, and any name colliding with another step or branch — steps and branches share ONE namespace (`AllStepNames`), because `{{steps.<name>.context}}` addresses both. `ValidateLoops` rejects a `goto` naming a branch (target the group) while allowing exit conditions to name one. `validateAgentRefs` requires every branch's effective agent to be headless; `collectAgentRefs`, `validatePromptIncludes` and the routine input guard all walk branches. `ParallelConfig.EffectiveBranch(i, group)` is the single place branch defaults are applied (agent and timeout fall back to the group's; an unset `summarization_strategy` becomes `last_message`, NOT the global step default) — the parsed config is never rewritten, so every consumer (engine, validators, daemon summaries, TUI) must go through it.
- **Step references mirror workflow references** — inside a workflow's `steps:`, a bare-string entry (`- planning`) is a *step reference* resolved by `resolveWorkflowSteps` against the same-named workflow in `cfg.globalPool` (the workflow this one overrides). Inline step mappings pass through; an inline step whose name matches a base step fully overrides it (replace-not-merge). Dropping a step = omitting it; adding = an inline entry with a new name. A ref to a step absent from the base — or a ref with no base workflow at all — is a hard error. A bare-string step is parsed via `StepConfig.UnmarshalYAML` (scalar → `StepConfig{Name, ref:true}`) and always resolved to a concrete step before validation.
- **`{{prompt.<name>}}` includes are files, validated at load time** — `PromptDirs(projectDir)` gives the two search roots (`<project>/.sakusen/prompts`, then `~/.sakusen/prompts` via `globalSakusenDir`), and `ExpandPromptIncludes` substitutes `<name>.md` (first hit wins, one trailing newline stripped). `validatePromptIncludes` runs in `Load()`/`LoadForProject()` after `appendTrackWorkflows`/`resolveAndValidateAgents` — and in `validateProject` for `sakusen validate` — over every templated string (`merge_conflicts.prompt`, workflow `summarizer_prompt`, step `prompt`/`summarization_prompt`), so a missing file, a malformed name (`[A-Za-z0-9_-]+` only), or a nested include is a HARD load error naming the workflow, step, field and searched paths. It only *validates*: the placeholder stays in the config and `internal/workflow` re-reads the file per step launch, so editing a shared passage needs no reload. There is no `prompts:` YAML map and no agent-level prompt — the unit of reuse is a passage of text, not a step or an agent.
- **Workflow entries have three shapes, all routed through `resolveFlat`** — an entry in the flat `workflows:` list (`WorkflowEntry`) is a scalar ref, a `- name: X` inline def, or the named-body sugar `- X: { ... }` (single key that isn't a known `WorkflowConfig` field; empty body = bare ref). `DiagnoseFileOnly`'s global-pool load is tolerant: a malformed/unresolvable `~/.sakusen.yml` yields no pool rather than failing project validation. `Diagnose` (the `sakusen validate` default) runs those file-only checks, then the `LoadForProject` pipeline via the shared `loadMerged`, so unresolved agent refs and a global config that can't load are errors (attributed via `globalTierError`); `--file-only` keeps single-file mode.
