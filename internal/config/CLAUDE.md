# internal/config — Configuration

`.sortie.yml` parsing, project type detection, workflow definitions. Load `/config` skill before making substantial changes.

## Critical Invariants

- **Loop goto must reference an earlier step** — validated at parse time; forward jumps or self-references create infinite loops
- **Summarization strategy affects step context capture** — `last_message` keeps the headless agent's result text; `summarize_chat` runs the configured `summarizer:` command over the chat log
- **Config merge hierarchy is strict** — `.sortie.yml` > `~/.sortie.yml` > global defaults; invalid configs halt the CLI
- **Agents merge per-slug across tiers** — `mergeAgents` overlays the project-tier `agents:` map onto the global tier; a slug redefined more locally wins wholesale (records are never field-merged). `validateAgents` runs in `Load()`/`LoadForProject()` only AFTER all tiers and workflows are merged: record shape (kebab-case slug, required `command`, mode ∈ {headless, tmux}, `resume_command`/`chat_log_command` tmux-only), explicit `agent:`/`default_agent:` refs must resolve (the implicit `"claude"` fallback is exempt and fails at step-run time instead), loop steps must not resolve to tmux agents, and `{{claude_command}}` in tmux-setup-command is rejected.
- **Removed keys are hard migration errors** — `claude:`, `yolo:`, `system_prompt:`, `allowed_summarization_models:` (top-level, via `checkRemovedProjectKeys` on the raw YAML; also step-level for the last one), and `print:`/`tmux:` (workflow and step level) all fail the load with instructive messages pointing at the `agents:`/`summarizer:` replacements — no silent back-compat mapping.
- **Track workflows are hidden and namespaced** — `.sortie/tracks/<slug>/workflows/*.yml` (project tier) and `~/.sortie/tracks/<slug>/workflows/*.yml` (global tier) register as `Hidden: true` workflows named `<slug>:<name>` via `appendTrackWorkflows`, called AFTER project-level resolution in `Load()`/`LoadForProject()` (never inside `loadProjectConfig`, which also runs for `~/.sortie.yml`). Project shadows global on identical namespaced names; there is no implicit same-name shadowing of ordinary workflows — track workflows are only reachable via their namespaced name.
- **Project string refs fall back to a global workflow pool** — after `~/.sortie.yml` is loaded, its resolved workflows (both inline and file-based under `~/.sortie/workflows/`) are snapshotted into `cfg.globalPool`. Project-level string refs in the flat `workflows:` list try the local `.sortie/workflows/` pool first, then `cfg.globalPool`. A project may override a global workflow by defining it inline or by adding a local `.sortie/workflows/<name>.yml`. Inline-vs-file collision is enforced only within a single config scope.
- **`on_complete` resolution is locality-based** — `Config.EffectiveOnComplete(workflowName)` is the single resolution point (the engine delegates to it). Precedence: project-scoped workflow `on_complete` > explicit project-level `on_complete` > global workflow `on_complete` > inherited/global/default. Workflows adopted from the global pool (and global-tier track workflows) are marked `FromGlobal: true` by the loader; `Config.OnCompleteFromProject` records that the project-tier `.sortie.yml` explicitly set `on_complete`. A global workflow's `on_complete` is a cross-project *default*, never a silent override of a project's explicit choice.
- **Step references mirror workflow references** — inside a workflow's `steps:`, a bare-string entry (`- planning`) is a *step reference* resolved by `resolveWorkflowSteps` against the same-named workflow in `cfg.globalPool` (the workflow this one overrides). Inline step mappings pass through; an inline step whose name matches a base step fully overrides it (replace-not-merge). Dropping a step = omitting it; adding = an inline entry with a new name. A ref to a step absent from the base — or a ref with no base workflow at all — is a hard error. A bare-string step is parsed via `StepConfig.UnmarshalYAML` (scalar → `StepConfig{Name, ref:true}`) and always resolved to a concrete step before validation.
- **Workflow entries have three shapes, all routed through `resolveFlat`** — an entry in the flat `workflows:` list (`WorkflowEntry`) is a scalar ref, a `- name: X` inline def, or the named-body sugar `- X: { ... }` (single key that isn't a known `WorkflowConfig` field; empty body = bare ref). `Diagnose`'s global-pool load is tolerant: a malformed/unresolvable `~/.sortie.yml` yields no pool rather than failing project validation.
